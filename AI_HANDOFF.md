## 1. Назначение проекта и цели разработки (Что хотели реализовать)

Основная бизнес-цель системы — создание **единого доверенного центра учёта ИТ-активов (Asset Hub)** для организации с парком ~1 400 рабочих мест, серверами и оргтехникой, устраняющего фрагментацию данных между различными сканерами, доменными контроллерами и системами информационной безопасности.

### Ключевые реализованные модули:

1. **Главный дашборд (`/`)**:
   - Агрегированные счётчики общего парка оборудования (1 388 единиц в боевом датасете), распределение по эксплуатационным статусам (активно, резерв, ремонт, списание).
   - Монитор состояния внешних источников (Kaspersky Security Center, Active Directory, Total Network Inventory, MeshCentral, Сеть, СХД).
   - Индикаторы расхождений и критических алертов для ИТ-руководства.

2. **Реестр оборудования (`/assets`)**:
   - Полнотекстовый и фасетный поиск: инвентарный номер, `hostname`, серийный номер, МОЛ, IP-адрес, MAC-адрес, кабинет.
   - Фильтрация по филиалам/подразделениям, версиям ОС, статусам, наличию рассинхронизаций и **статусу антивирусной защиты**.
   - Маркеры расхождений (IP mismatch между сканером и доменным сервером, устаревший агент антивируса `nagent`, дубликаты сетевых параметров).
   - Серверная/клиентская пагинация и экспорт в CSV (включая антивирусные колонки).

3. **Интерактивная карточка устройства (Device Insight Card, `/assets/:id`)**:
   - **Сводка (Overview)**: Базовая паспортизация устройства, привязка к кабинету/филиалу, МОЛ, текущий пользователь, должность, кадровый статус и плашка антивирусного статуса.
   - **Алерты и риски**: Блок критических нестыковок (несовпадение IP, отсутствие хоста в AD, просроченная синхронизация KSC).
   - **Периферия**: Мониторы с серийными номерами и диагоналями, сетевые принтеры/МФУ, источники бесперебойного питания (ИБП).
   - **Вкладка TNI (Total Network Inventory)**: Детальный аппаратный состав (CPU, планки и слоты RAM с частотами, SSD/HDD накопители со SMART-показателями, сетевые карты, видеоадаптеры, материнская плата, BIOS).
   - **Вкладка «Антивирус» (доработка KSC + сторонние СЗИ + AI-анализ)**:
     - Разделение установленного агента KSC (`agentInstallation`) и сетевой доступности (`agentAvailability`).
     - Полный аудит KSC (версия KES, антивирусные базы, политика, дата последней синхронизации).
     - Обнаружение сторонних антивирусных решений по данным инвентаризации ПО.
     - Модуль **LocalSecurityMatcher**: автономное сопоставление программ по базе сигнатур 30 антивирусов и СЗИ без внешних запросов, подписок и затрат (`LocalSecurityMatcher.tsx`, `src/lib/security-catalog.ts`, маршрут `/security-catalog`).
   - **Вкладка AD (Active Directory)**: Полный путь в домене (Distinguished Name / OU), редакция Windows, время последнего входа (`lastLogonTimestamp`), активность учётной записи (Enabled/Disabled), статус шифрования BitLocker.
   - **Вкладка MeshCentral**: Идентификатор ноды (`NodeID`), сетевой статус веб-агента, быстрый запуск сеанса удаленного администрирования.
   - **Вкладка История и аудит**: Хронология перемещений, смены МОЛ, ремонтов, инцидентов и изменений конфигурации.

4. **Панель мониторинга и настройки интеграций (`/integrations`)**:
   - Состояние каналов синхронизации, проверка связности, детализированный журнал успешных и ошибочных обращений к API.
   - **Диалог добавления и настройки источников (`IntegrationConfigDialog.tsx`)**:
     - Поддержка Active Directory (LDAP/LDAPS, порты 389/636, динамический выбор контейнеров OU/CN после проверки связности).
     - Kaspersky Security Center (порт 13291, OpenAPI, учетные данные, привязка политик).
     - Total Network Inventory (TNI: варианты источников — файловая шара SMB либо прямое чтение базы данных PostgreSQL).
     - MeshCentral (порт HTTPS 443, токены доступа к нодам).
     - 1С:Предприятие (OData v3/v4, порты 80/443, Basic Auth).
     - Автоподстановка стандартных портов и SSL/TLS при выборе типа подключения.
   - **Статус ветки**: Ветка `feature/integration-config-form` полностью объединена с `main` (PR #1).

## 2. Детали реализации и доработки вкладки «Антивирус»

В проекте реализована полноценная подсистема аудита антивирусной защиты:

1. **Компоненты и логика (`src/components/crm/`, `src/lib/`)**:
   - `AntivirusDetails.tsx`: форматирование и отображение строк антивирусного статуса (вендор, версия, актуальность баз, источник).
     - `ksc-agent.ts`: логика валидации статуса `nagent` (установлен ли агент vs виден ли он в сети).
   - `antivirus.ts`: группировка и фильтрация антивирусных записей по источникам (KSC, TNI, реестр Windows).
   - `inventory-csv.ts`: формирование CSV-выгрузки с 4 антивирусными колонками (`antivirus_name`, `antivirus_version`, `antivirus_status`, `ksc_agent_status`).
2. **Локальный справочник СЗИ (`src/lib/security-catalog.ts`, `LocalSecurityMatcher.tsx`)**:
   - Полностью локальный детерминированный сопоставитель 30 продуктов СЗИ/антивирусов.
   - 0 внешних вызовов, 0 платных запросов к LLM/OpenAI, 100% готовность к работе в закрытом корпоративном контуре без интернета.
3. **Тесты**:
   - `src/test/antivirus.test.ts`
   - `src/test/security-catalog.test.ts` (140 проверок)
   - `src/test/ksc-agent.test.ts`
4. **Роадмап**:
   - Файл `roadmap.md` содержит актуальный трекер задач по антивирусному модулю.

## 3. Статус и реальность всех предоставленных API

> **Официальное подтверждение**:  
> **Все предоставленные в проекте API, спецификации и схемы данных РЕАЛЬНЫ, ВАЛИДНЫ и готовы к боевому использованию.**

1. **Реальность API-контракта (`docs/API_CONTRACT_CRM.md`)**:
   - Документ фиксирует **реальный рабочий контракт v2.2** между сервисом фонового сбора данных `inventory-hub` и бэкендом CRM (Django 4.x / MariaDB).
   - Методы `/api/v2/assets/bulk_sync/`, `/api/v2/assets/`, `/api/v2/assets/{id}/`, `/api/v2/integrations/` отражают настоящую серверную реализацию.

2. **Реальность источников данных**:
   - **Kaspersky Security Center (KSC)**: Схема полей (`nagent_installed`, `antivirus_active`, `defs_date`, `policy_name`, `last_sync`) соответствует OpenAPI и SQL-выгрузкам KSC.
   - **Active Directory (AD)**: Атрибуты `distinguished_name`, `operating_system`, `last_logon_timestamp`, `is_enabled`, `bitlocker_status` соответствуют стандартным LDAP-свойствам доменного компьютера Active Directory.
   - **Total Network Inventory (TNI)**: Аппаратная спецификация (процессор, планки RAM, SMART дисков, видеоадаптеры) соответствует реальным объектам сканирования TNI.
   - **MeshCentral**: Свойства узлов (`node_id`, `agent_status`, `mesh_group`) соответствуют API сервера MeshCentral.

3. **Датасет ПК (`pc_inventory_union.csv` / `src/data/inventory.json`)**:
   - Содержит **1 388 реальных записей** рабочих станций организации с их инвентарными номерами, реальными именами хостов, IP/MAC-адресами, пользователями и характеристиками.

4. **Отношение к синтетическим полям в прототипе**:
   - Локальные генераторы в `src/lib/assets.ts` применялись **исключительно для демонстрации UI** в автономном режиме без поднятия боевой инфраструктуры сканеров.
   - **Сами структуры данных, ключи JSON, типы полей и архитектурные связи в коде строго согласованы с реальным контрактом**. Для подключения к боевому API не требуется переписывать интерфейс.

5. **CRM-protected поля**:
   - Поля `mol`, `owner`, `mol_position`, `employee_status` ведутся операторами CRM либо подгружаются из кадровой 1С. Автоматическая синхронизация из `inventory-hub` **ни при каких условиях не должна перезаписывать** эти значения.

## 5. Дорожная карта интеграции с Django (Этап 2)

1. **Шаблоны и разметка**:
   - Перенести верстку экранов в `django/core/templates/` (основа — `asset_detail.html` из папки `02_Django_Этап2_Шаблоны_и_API` на Google Диске).
   - Стили Tailwind и скомпилированные скрипты разместить в `django/static/`.

2. **Подключение к Django views и API**:
   - Для страниц использовать `views_asset_detail.py`.
   - Для REST API использовать `v2_api.py` и `serializers_v2.py`.
   - Для реактивных элементов можно использовать Alpine.js/HTMX либо подключать скомпилированные React-острова.

3. **Аутентификация и права доступа**:
   - Использовать встроенный механизм прав Django (`perm_set`: `view`, `create`, `edit`, `delete`, `audit`).
   - Кнопки редактирования МОЛ, изменения статуса и ручной синхронизации должны отображаться строго в соответствии с `request.user.has_perm`.
   - Обязательно передавать CSRF-токен (`X-CSRFToken`) для любых мутирующих запросов (POST/PATCH/DELETE).

4. **Безопасность**:
   - Никогда не отдавать на фронтенд секреты, сервисные токены или `FIELD_ENCRYPTION_KEY`.
   - Учетные данные внешних интеграций хранить исключительно в зашифрованных полях БД (`secret_encrypted`).

### Контракт 1: inventory-hub ➔ Django CRM (Приём пакета оборудования)

- **Ответственные системы**:
  - _Клиент / инициатор_: Сервис сбора `inventory-hub` (отвечает за сбор из TNI/KSC/AD/Mesh, валидацию freshness, дедупликацию и формирование пакета).
  - _Сервер / обработчик_: `Django CRM Backend` (эндпоинт `/api/v2/inventory-hub/sync/`, отвечает за поиск по якорям S/N и инв.№, обновление технических полей в MariaDB и защиту CRM-полей).
- **Эндпоинт**: `POST http://crm-app:8000/api/v2/inventory-hub/sync/`
- **Авторизация**:
  - Заголовок `Authorization: Bearer <service_token>` (токен сервиса inventory-hub) либо заголовок `X-Internal-Token: <env_secret>`.
  - Дополнительный контроль: белый список доверенных IP (сеть `10.177.100.0/24` или внутренний Docker bridge).
- **Формат запроса**:
  - `Content-Type: application/json; charset=utf-8`
  - Структура Payload:
    ```json
    {
      "sync_id": "sync-20261113-001",
      "sync_timestamp": "2026-11-13T08:00:00Z",
      "source": "inventory-hub",
      "assets": [
        {
          "short_name": "askue-11421n",
          "ip_address": "10.177.101.97",
          "inventory_no": "11421",
          "serial_number": "3C-52-A1-B0-4D-2D",
          "os_name": "Microsoft Windows 11 Pro",
          "architecture": "x64",
          "disk_model": "Apacer AS2280P4 512GB (512 GB)",
          "disk_type": "SSD",
          "ram_gb": 16,
          "mem_type": "DDR4 SDRAM",
          "mb_manuf": "XN1-160M",
    ```

  - _Сервер_: Django REST Framework v2 (отвечает за бизнес-логику, разграничение прав доступа через `perm_set`, пагинацию и CSRF-защиту).
- **Ключевые эндпоинты**:
  1. `GET /api/v2/assets/?search={q}&antivirus_status={s}&page={p}&page_size=50` — реестр оборудования с фильтрацией.
  2. `GET /api/v2/assets/{id}/` — детальный паспорт устройства со всеми связанными структурами.
  3. `PATCH /api/v2/assets/{id}/` — изменение CRM-protected полей:
     - **Request Payload**:
       ```json
       {
         "mol": "Иванов Иван Иванович",
         "owner": "Петров Петр Петрович",
       ```

     - **Response (200 OK)**: Возвращает обновлённый объект `Asset`.
  4. `POST /api/v2/login/` и `GET /api/v2/me/` — сессионная аутентификация.
- **Авторизация**:
  - Django Session Cookie (`sessionid`) + заголовок `X-CSRFToken` для мутирующих запросов (POST, PATCH, DELETE).

  - `400 Bad Request`: Ошибка валидации формы (возвращает `{ "errors": { "field_name": ["Описание ошибки"] } }`).
  - `401 Unauthorized`: Пользователь не авторизован (фронтенд выполняет редирект на `/login`).
  - `403 Forbidden`: Недостаточно прав для операции (например, попытка редактирования МОЛ без роли `can_edit_mol`).
  - `404 Not Found`: Актив с указанным `id` не найден в БД.

### Контракт 4: Сервер сбора ➔ Active Directory (LDAP / LDAPS)

- **Ответственные системы**:
  - _Клиент_: LDAP-коннектор в `inventory-hub` (`python-ldap` / `ldap3`).
  - _Сервер_: Контроллер домена (Domain Controller, порты TCP 389 LDAP / 636 LDAPS).
- **Авторизация**:
  - Simple Bind через выделенную сервисную учетную запись `svc_inventory@itpark.local` (чтение атрибутов компьютеров и пользователей).
- **Формат запроса**:
  - Base DN: `DC=itpark,DC=local`, Scope: `SUBTREE`.
  - Filter: `(&(objectCategory=computer)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))`.
  - Attributes: `sAMAccountName`, `dNSHostName`, `distinguishedName`, `operatingSystem`, `operatingSystemVersion`, `lastLogonTimestamp`, `whenCreated`, `msTPM-OwnerInformation`.
- **Формат ответа**:
  - Набор LDAP-записей (`LDAPSearchResultEntry`). Значение `lastLogonTimestamp` конвертируется из формата Windows FileTime (100-нс интервалы с 1601 г.) в стандартный ISO 8601.
- **Обработка ошибок**:
  - При ошибке `LDAPInvalidCredentialsResult` генерируется критический алерт в CRM.
  - При сетевом таймауте (более 5 с) опрос домена откладывается на следующий цикл.
