## 1. Назначение проекта и цели разработки (Что хотели реализовать)

Основная бизнес-цель системы — создание **единого доверенного центра учёта ИТ-активов (Asset Hub)** для организации с парком ~1 400 рабочих мест, серверами и оргтехникой, устраняющего фрагментацию данных между различными сканерами и службами.

### Ключевые реализованные и заложенные модули:

1. **Главный дашборд (`/`)**:
   - Агрегированные счётчики общего парка оборудования (1 388 единиц в боевом датасете), распределение по эксплуатационным статусам (активно, резерв, ремонт, списание).
   - Монитор состояния внешних источников (Kaspersky Security Center, Active Directory, Total Network Inventory, MeshCentral, Сеть, СХД).
   - Индикаторы расхождений и критических алертов для ИТ-руководства.

2. **Реестр оборудования (`/assets`)**:
   - Полнотекстовый и фасетный поиск: инвентарный номер, `hostname`, серийный номер, МОЛ, IP-адрес, MAC-адрес, кабинет.
   - Фильтрация по филиалам/подразделениям, версиям ОС, статусам и наличию рассинхронизаций.
   - Маркеры расхождений (IP mismatch между сканером и доменным сервером, устаревший агент антивируса `nagent`, дубликаты сетевых параметров).
   - Серверная/клиентская пагинация.

3. **Интерактивная карточка устройства (Device Insight Card, `/assets/:id`)**:
   - **Сводка (Overview)**: Базовая паспортизация устройства, привязка к кабинету/филиалу, МОЛ, текущий пользователь, должность и кадровый статус.
   - **Алерты и риски**: Блок критических нестыковок (несовпадение IP, отсутствие хоста в AD, просроченная синхронизация KSC).
   - **Периферия**: Мониторы с серийными номерами и диагоналями, сетевые принтеры/МФУ, источники бесперебойного питания (ИБП).
   - **Вкладка TNI (Total Network Inventory)**: Детальный аппаратный состав (CPU, планки и слоты RAM с частотами, SSD/HDD накопители со SMART-показателями, сетевые карты, видеоадаптеры, материнская плата, BIOS).
   - **Вкладка KSC (Kaspersky Security Center)**: Состояние сетевого агента `nagent`, версия баз антивируса, дата последнего сканирования, примененные групповые политики ИБ.
   - **Вкладка AD (Active Directory)**: Полный путь в домене (Distinguished Name / OU), редакция Windows, время последнего входа (`lastLogonTimestamp`), активность учётной записи (Enabled/Disabled), статус шифрования BitLocker.
   - **Вкладка MeshCentral**: Идентификатор ноды (`NodeID`), сетевой статус веб-агента, быстрый запуск сеанса удаленного администрирования.
   - **Вкладка История и аудит**: Хронология перемещений, смены МОЛ, ремонтов, инцидентов и изменений конфигурации.

4. **Панель мониторинга интеграций (`/integrations`)**:
   - Состояние каналов синхронизации, проверка связности, детализированный журнал успешных и ошибочных обращений к API.

## 2. Статус и реальность всех предоставленных API

> **Официальное подтверждение**:  
> **Все предоставленные в проекте API, спецификации и схемы данных РЕАЛЬНЫ, ВАЛИДНЫ и готовы к боевому использованию.**

1. **Реальность API-контракта (`docs/API_CONTRACT_CRM.md`)**:
   - Документ фиксирует **реальный рабочий контракт v2.2** между сервисом фонового сбора данных `inventory-hub` и бэкендом CRM (Django 4.x / MariaDB).
   - Методы `/api/v2/assets/bulk_sync/`, `/api/v2/assets/`, `/api/v2/assets/{id}/`, `/api/v2/integrations/` отражают настоящую серверную реализацию (см. также `serializers_v2.py`, `v2_api.py`, `models_extension.py` в материалах этапа 2 на Google Диске).

2. **Реальность источников данных**:
   - **Kaspersky Security Center (KSC)**: Схема полей (`nagent_installed`, `antivirus_active`, `defs_date`, `policy_name`, `last_sync`) соответствует OpenAPI и SQL-выгрузкам KSC.
   - **Active Directory (AD)**: Атрибуты `distinguished_name`, `operating_system`, `last_logon_timestamp`, `is_enabled`, `bitlocker_status` соответствуют стандартным LDAP-свойствам доменного компьютера Active Directory.
   - **Total Network Inventory (TNI)**: Аппаратная спецификация (процессор, планки RAM, SMART дисков, видеоадаптеры) соответствует реальным объектам сканирования TNI.
   - **MeshCentral**: Свойства узлов (`node_id`, `agent_status`, `mesh_group`) соответствуют API сервера MeshCentral.

3. **Датасет ПК (`pc_inventory_union.csv` / `src/data/inventory.json`)**:
   - Содержит **1 388 реальных записей** рабочих станций организации с их инвентарными номерами, реальными именами хостов, IP/MAC-адресами, пользователями и характеристиками.

4. **Отношение к синтетическим полям в прототипе**:
   - Локальные генераторы в `src/lib/assets.ts` применялись **исключительно для демонстрации UI** в автономном режиме без поднятия боевой инфраструктуры сканеров.
   - **Сами структуры данных, ключи JSON, типы полей и архитектурные связи в коде строго согласованы с реальным контрактом**. Для подключения к боевому API не требуется переписывать интерфейс — достаточно заменить локальный источник данных на вызовы API.

5. **CRM-protected поля**:
   - Поля `mol`, `owner`, `mol_position`, `employee_status` ведутся операторами CRM либо подгружаются из кадровой 1С. Автоматическая синхронизация из `inventory-hub` **ни при каких условиях не должна перезаписывать** эти значения.

## 3. Стек технологий и запуск проекта

- **Фреймворк**: React 19, TypeScript
- **Маршрутизация**: TanStack Start / TanStack Router
- **Стилизация**: Tailwind CSS v4, Radix UI Primitives, Lucide Icons
- **Таблицы и данные**: TanStack Table, Recharts

### Команды:
```bash
# Установка зависимостей
bun install  # или npm install

# Запуск dev-сервера (http://localhost:3000)
bun dev      # или npm run dev

# Сборка production-бандла
bun run build  # или npm run build

# Запуск тестов
bun test     # или npm test
```

## 4. Дорожная карта интеграции с Django (Этап 2)

Если проект переносится в существующий Django 4.x бэкенд:

1. **Шаблоны и разметка**:
   - Перенести верстку экранов в `django/core/templates/` (основа — `asset_detail.html` из папки `02_Django_Этап2_Шаблоны_и_API` на Google Диске).
   - Стили Tailwind и скомпилированные скрипты разместить в `django/static/`.

2. **Подключение к Django views и API**:
   - Для страниц использовать `views_asset_detail.py`.
   - Для REST API использовать `v2_api.py` и `serializers_v2.py`.
   - Для реактивных элементов (фильтрация, табы, раскрывающиеся списки) можно использовать Alpine.js/HTMX либо подключать скомпилированные React-острова.

3. **Аутентификация и права доступа**:
   - Использовать встроенный механизм прав Django (`perm_set`: `view`, `create`, `edit`, `delete`, `audit`).
   - Кнопки редактирования МОЛ, изменения статуса и ручной синхронизации должны отображаться строго в соответствии с `request.user.has_perm`.
   - Обязательно передавать CSRF-токен (`X-CSRFToken`) для любых мутирующих запросов (POST/PATCH/DELETE).

4. **Безопасность**:
   - Никогда не отдавать на фронтенд секреты, сервисные токены или `FIELD_ENCRYPTION_KEY`.
   - Учетные данные внешних интеграций хранить исключительно в зашифрованных полях БД (`secret_encrypted`).
