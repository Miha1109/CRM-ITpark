# API-контракт между inventory-hub и CRM-itpark

Дата: 2026-11-10  
Статус: проект  
Источник правды: этот документ

## 1. Общая схема взаимодействия

```
inventory-hub (сборщик)                          CRM-itpark (хранилище + веб)
│                                                                              │
│  1. GET /api/v2/integrations/   ◄─── берёт креды к TNI/KSC/AD/Mesh            │
│  2. Собирает данные из источников                                              │
│  3. Дедуплицирует, фильтрует шум, проверяет freshness                          │
│  4. POST /api/v2/inventory-hub/sync/  ─────────────────────────────────────►│
│                 готовый JSON с устройствами                                   │
│                                                                                │
│  CRM принимает, записывает в таблицу Asset (MariaDB crmdb)                    │
│  CRM обогащает данными из 1С (МОЛ, должность, статус) через свои механизмы    │
│                                                                                │
└───────────────────────────────────────────────────────────────────────────────┘
```

inventory-hub и CRM — **два отдельных репозитория и две отдельные БД**.  
Обмен данными происходит **только через HTTP API**, общая БД не используется.

## 2. Endpoint приёма инвентаря в CRM

### 2.1. Адрес
```
POST http://crm-app:8000/api/v2/inventory-hub/sync/
```

### 2.2. Метод
`POST`

### 2.3. Аутентификация
- `Authorization: Bearer <token>` — токен службы inventory-hub, выданный CRM.
- Альтернатива: `X-Internal-Token: <секрет из ENV CRM>`.
- CRM проверяет, что запрос приходит из доверенной сети (только `10.177.100.46` или контейнер inventory-hub).

## 3. CRM-protected поля (НЕ принимать из inventory-hub)

Следующие поля **не принимаются** из inventory-hub и **не перезаписываются** при импорте. Они заполняются внутри CRM (вручную или через интеграцию с 1С):

| Поле | Кто заполняет | Источник |
|------|---------------|----------|
| `mol` | CRM / 1С ЗУП | Сотрудник, ответственный за ПК |
| `owner` | CRM / 1С Бух | Владелец актива |
| `mol_position` | CRM / 1С ЗУП | Должность МОЛ |
| `employee_status` | CRM / 1С ЗУП | Статус сотрудника (работает / уволен) |
| `id` | CRM (авто) | Первичный ключ |
| `created_at`, `updated_at` | CRM (авто) | Время создания / изменения |

**Правило:** Если в теле запроса приходят эти поля — CRM **игнорирует их** и не перезаписывает. Интерфейс не должен позволять inventory-hub перезаписать эти поля.

---

### 2.6. Коды ответов API

| Код | Значение |
|-----|----------|
| `200 OK` | Все активы приняты |
| `207 Multi-Status` | Часть принята, часть требует проверки (конфликты якорей, дубли) |
| `400 Bad Request` | Неверный JSON или отсутствуют обязательные поля |
| `401 Unauthorized` | Нет токена или неверный токен inventory-hub |
| `403 Forbidden` | IP-адрес отправителя не в доверенном списке |
| `422 Unprocessable Entity` | Некоторые активы не прошли валидацию (например, нет имени и нет IP) |
| `500 Internal Server Error` | Ошибка записи в CRM |

## 3. Логика импорта в CRM (создание / обновление / конфликты)

### 3.1. Поиск существующего актива

CRM ищет существующую запись `Asset` по приоритету:

1. По `serial_number` (если передан и не пустой) — основной якорь.
2. По `inventory_no` (если передан и не пустой) — второй якорь.
3. По паре `short_name` + `ip_address` (если оба есть) — третий якорь.

### 3.2. Если актив найден

CRM обновляет только **технические поля**, которые пришли в запросе и не находятся в списке CRM-protected:
- `os_name`, `architecture`, `ram_gb`, `cpu`, `cpu_manufacturer`, `cpu_model`, `cpu_cores`, `disk_model`, `disk_type`, `mb_manuf`, `mb_model`, `monitors`, `printers`, `current_user`, `mac_address`, `observed_at`, `source`, `check_flag`, `ip_address` (если изменился и якорь — serial/inventory_no совпал).

**Важно:** Поля `mol`, `owner`, `mol_position`, `employee_status` **не затираются**, даже если в запросе они отсутствуют.

### 3.3. Если актив не найден

CRM создаёт новую запись `Asset` со всеми полученными техническими полями. Поля `mol`, `owner`, `mol_position`, `employee_status` остаются `NULL` до ручного заполнения или синхронизации с 1С.

### 3.4. Конфликты

Если при импорте обнаруживается, что:
- Один и тот же `serial_number` уже принадлежит другому `short_name` — CRM ставит флаг на проверку и не перезаписывает автоматически.
- Один и тот же `inventory_no` уже есть у другого актива с другим серийным номером — аналогично, флаг на проверку.

Такие записи помечаются в CRM флагом «требует ручной проверки» и не импортируются автоматически.

## 4. Направления передачи данных

| Данные | inventory-hub → CRM | CRM → inventory-hub |
|--------|---------------------|---------------------|
| Список ПК с железом (ОС, ОЗУ, ЦП, диск, мониторы, принтеры, MAC, S/N) | ✅ Да | ❌ Нет |
| Короткое имя, IP, инв.№, серийник | ✅ Да | ❌ Нет |
| Дата наблюдения, источник, флаги проверки | ✅ Да | ❌ Нет |
| Параметры подключения к TNI/KSC/AD/Mesh (сервер, порт, логин, зашифрованный пароль) | ❌ Нет | ✅ CRM отдаёт через `GET /api/v2/integrations/` (только для авторизованного inventory-hub) |
| МОЛ, владелец, должность, статус сотрудника | ❌ Нет | ✅ CRM хранит sama (из 1С или ручного ввода) |
| Журнал аудита изменений актива | ❌ Нет | ✅ CRM хранит sama |

## 5. Взаимодействие с 1С (CRM обогащает данные после импорта)

После того как inventory-hub загрузил технические данные в CRM, CRM независимо от inventory-hub обогащает их:

1. **1С ЗУП** — CRM загружает список сотрудников (работающие, уволенные), их должности и статус.
2. **1С Бухгалтерия** — CRM загружает таблицу соответствия: `инвентарный № → ответственный (МОЛ)`.
3. CRM сопоставляет по `inventory_no` (или `serial_number`) и заполняет поля `mol`, `mol_position`, `employee_status` в таблице `Asset`.
4. Инвентаризация (inventory-hub) **не участвует** в этом процессе и не перезаписывает эти поля.

Пример цикла:
```
inventory-hub → CRM: Asset с inventory_no=11421, serial=3C-52-A1-B0-4D-2D
CRM → 1С Бухгалтерия: «Кто ответственный за инв.№ 11421?»
1С → CRM: «Иванов И.И., ведущий инженер, работает»
CRM обновляет Asset.mol = 'Иванов И.И.', employee_status = 'working'
```

---

## 6. Что НЕ передаётся из inventory-hub в CRM

| Поле | Причина |
|------|---------|
| `mol`, `owner`, `mol_position`, `employee_status` | CRM-only поля, заполняются из 1С или вручную |
| Внутренние промежуточные флаги отладки inventory-hub | Не нужны в CRM |
| Временные идентификаторы сканов KSC/TNI | Внутренние для inventory-hub |
| Пароли и токены подключения к источникам | Хранятся только в CRM `Integration.secret_encrypted`, inventory-hub забирает их на время сессии и не хранит постоянно |

## 7. Рекомендуемый порядок действий при внедрении

1. Согласовать JSON-контракт поля `assets[]` между разработчиками inventory-hub и CRM (этот документ).
2. Реализовать в CRM эндпоинт `POST /api/v2/inventory-hub/sync/` с аутентификацией.
3. Реализовать в inventory-hub клиент, который забирает `Integration` из CRM API, собирает данные из источников, фильтрует и дедуплицирует, отправляет результат в CRM.
4. Протестировать на пилотной выборке (например, только подсети `10.177.100.0/24`).
5. Внедрить в CRM ручную кнопку «Синхронизировать с inventory-hub» и/или Celery-задачу по расписанию.

---

## 8. Пример процесса синхронизации

```
1. Администратор в CRM нажимает «Синхронизировать инвентарь»
2. CRM → inventory-hub: GET /api/v2/integrations/ (получает креды к TNI/KSC/AD/Mesh)
3. inventory-hub: собирает данные из источников, дедуплицирует, фильтрует
4. inventory-hub → CRM: POST /api/v2/inventory-hub/sync/ (готовый JSON)
5. CRM → MariaDB: создаёт/обновляет записи Asset
6. CRM → 1С: обогащает МОЛ/должность/статус
7. Пользователь CRM: видит обновлённые карточки устройств
```
